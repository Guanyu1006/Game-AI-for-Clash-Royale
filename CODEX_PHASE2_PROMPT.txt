# 第二阶段执行规格：固定版本原生战斗、真实回放重建、可信轨迹与游戏画面

请读取并执行本文件，将当前项目推进到：一套可以离线重建真实对局回放、输出带质量证据的训练轨迹、供 agent 批量实验，并能够显示配套游戏画面的固定版本环境。

这是一项实施任务，不是只提交方案或资料综述。请自主审计、下载、复现、适配、运行、修复、验证和编写中文说明。先制定计划，随后立即开始，不等待我逐项催促。若当前环境支持持续 Goal，请为本阶段建立持续目标；只有本阶段全部硬验收通过才可标记完成。

一、目标、范围与现有基线

1. 我的主要需求是卡牌交互尽可能忠于一个明确的真实游戏版本，让对应版本的真实回放能够被重建并用于学习。画面应尽量使用配套游戏客户端/原生渲染，以便观看、调试和展示。渲染按需开启，批处理训练不应依赖逐帧绘图。
2. 官方账号、官方在线对战和生产服务器不能成为训练或验收依赖。不要登录我的官方账号，不向官方天梯提交自动化动作。本阶段不要求实现商城、付费、排行榜和完整账号生态。
3. 可以借鉴私服的本地会话、对局配置和命令驱动方式，但仅有登录/大厅/命令转发不能算达成本阶段。主交付必须能够真正计算战斗、推进状态、确认动作和产生终局。
4. 保留已有 royale_ai、baseline/mvp_v0_1 和 royale_lab 校准v2平台、模型、700局评估及验收证据，作为可对比基线。旧模拟器可以用于诊断和回归，不得冒充本阶段原生后端，不得把旧测试数字直接记成本阶段成果。
5. 本阶段不承诺当前官方版本全部组合百分之百一致。必须固定实际可复现版本，用独立证据说明能确认到什么程度；同一原生程序也可能因数据、等级、初始化或命令转换错误而产生不同结果。

先读取 CODEX_BUILD_PROMPT.txt、STATUS.md、DELIVERY_REPORT.md、docs/ARCHITECTURE.md、docs/ENGINE_GUIDE.md、docs/SERVER_SELECTION.md、docs/audits/PRIVATE_SERVERS.md、docs/research/DATASETS.md，以及 royale_lab 的后端、观测、策略和训练接口。第一阶段规格用于理解基线；本阶段新增验收以本文件为准，不重复已完成的30论文/15项目任务。

四、固定版本与完整来源锁定

选择“引擎能够运行、数据能够匹配、结果能够验证”的版本；不强求最新，但不能悄悄用旧版本重放不兼容的新卡/进化/英雄数据。

建立 machine-readable 的 version_manifest.json 与兼容性报告，至少记录：

- 引擎/客户端构建号、平台、ABI、原生库SHA256、封装源码commit与本地补丁hash。
- 卡牌/单位/弹道/效果等实际使用数据和资源的SHA256，平衡日期及其证据；不知道则写unknown。
- 卡牌ID映射、等级与塔等级/塔兵种、进化/技能/形态、竞技场与模式、终局规则。
- tick频率、时间原点、坐标单位/精度/原点、左右/上下视角变换，以及动作在tick中的执行顺序。
- 数据集revision、schema、原始文件hash、筛选规则和版本兼容范围。

不能只凭“版本号相同”认定完整一致。启动、重放、加载轨迹及训练时检查版本指纹；不兼容必须拒绝或明确分组，不静默回落至已有近似引擎。建立受支持/不支持/未验证的卡牌与机制范围；不使用旧平台173行作为新后端覆盖分母。

五、真实数据取得、解析与转换

优先使用包含时序动作的真实回放资料，如 IL_Replay；先核实许可、revision、字段和原始来源，下载小样本检查兼容性，再扩至本阶段正式批次。不要把普通战绩摘要当成完整回放，也不要把历史视频转录的推断事件写成服务端确认事件。

保留不可变原始数据，另建转换层，输出统一episode配置与动作journal。每条动作尽量保存：source_episode_id、原始事件序号、player、card/ability、原始与归一化坐标、原始时间、目标tick、动作语义、来源和转换器版本。

需要实际解决或明确记录：

1. 双方卡组、等级、塔、进化和形态的配置映射。
2. 初始手牌、轮转、随机种子、起始tick和特殊模式信息是否存在；缺失信息不能伪造成已知。
3. 时间戳代表决策/点击、入队、部署还是实体出现。部署延迟不能套用另一条流水线的固定值。
4. 坐标、玩家视角、同tick多事件顺序、卡牌ID与手牌槽位、Mirror/技能等转换。
5. 缺字段、重复事件、异常顺序、非法坐标、不可用卡牌和不兼容版本的处理。

若需枚举初始轮转/种子等假设，应限制搜索空间、记录假设与选择依据、保留所有尝试；不能利用测试集最终结果反复调参后，再把同一批数据当作独立精度评估。

对每局建立原始→解析→配置→执行的可追溯链。不得为匹配胜负而删除真实动作、挪动下牌时间、修改血量、传送单位或注入最终结果。必要转换只能基于预先声明的格式/版本规则，并有小样本验证。

六、真正离线的原生战斗后端

实现可替换的 BattleBackend 适配，复用现有工程的接口思想而非强行沿用旧ID、坐标和10Hz约定。至少支持：

create/reset、configure_match、advance_exact_ticks、observe_visible、debug_state、submit_action、execution_feedback、result、export_journal、replay_from_start、close。

- WAIT、卡牌、落点、时机和受支持的技能必须明确建模；不支持的动作应报错，不能忽略后继续统计成功。
- 区分planned、queued、accepted、executed、rejected及unknown状态，记录请求ID和实际执行tick；用原生事件、费用、手牌或实体变化确认结果。
- 支持可重复reset、批量多局、终局、超时、进程崩溃和断连处理。通信失败后不能盲目重发可能已执行的动作；应查询同步点或从已验证日志恢复。
- 原生后端完整复制若不可用，允许先用精确初始化+已执行journal重演恢复，报告成本和验证结果；不能宣传为常数成本snapshot。
- 确认多个worker是否隔离；必要时每进程一引擎。单实例运行也要有批处理队列与恢复能力，不能用并发参数冒充实际并行。

“离线”必须实证：依赖准备完成后，在阻断外部网络、允许本机控制通信的环境中，从冷启动完成至少一局真实回放和一局agent对战。使用项目内隔离环境/可验证的等效网络隔离，不擅自修改全局防火墙。仅日志中没看见联网不等于证明了离线；若无法执行隔离，明确该验收未通过。

官方及第三方私服的远程服务不能参与正式回放计算。需要本地启动壳、资源缓存或会话服务时，应明确实现它们，并记录其实际职责。

七、回放重建、质量等级与一致性证据

先做少量回放的逐事件调试，再冻结一份不少于100局真实回放的正式验收清单，保留完整分母、原始ID与选择规则。按实际数据尽量覆盖多卡组、双方视角及版本内特殊机制。把开发/校准回放与正式验收回放分开，不能只挑容易成功的局而不披露筛选。

每局分别记录以下状态，不能用一个passed掩盖所有维度：

- parse_valid：结构可解析；不代表能够重放。
- runtime_replayable：原生环境能执行、无未解释的动作缺失；不代表官方轨迹一致。
- deterministic：同输入多次运行的规范化状态/事件序列相同。
- outcome_consistent：与来源提供的胜者、皇冠、终局时间/塔血等可用字段逐项比较，缺失字段为unknown。
- trajectory_validated：与独立取得的录像、帧、状态锚点或其他有效参考进行时序对照；若没有参考只能写not_available。

“同程序重复运行一致”不能充当官方一致证据；“胜负相同”不能充当逐交互一致证据。来自同一封装器生成的两份状态也不算独立真值。

报告动作输入数、入队/执行/拒绝/未知数、第一处分歧tick、缺失事件、塔血/位置/伤害等可比较误差、终局差异、失败原因和恢复命令。误差容限必须有单位和依据；区分精确值、浮点/采样误差、视觉测量不确定性。

至少选择10局在独立reset后各重复3次，比较规范化状态和事件哈希；排除地址、wall clock、渲染帧号等非语义字段，不能排除血量、坐标、队列等实质差异以制造一致。

至少建立20个版本相关关键交互夹具，涵盖本版本支持的部署/费用/轮转、桥与拉扯/索敌、攻击时序、法术、死亡衍生及特殊机制。内部回归与外部对照分别标记；不支持的进化/英雄不得以空测试通过。

汇总所有尝试局的成功、失败、未知及排除原因；另给可训练子集。不能仅过滤不一致的局后宣称“100%还原”。分析失败筛选是否偏向特定卡组、机制和结果。

八、可信训练轨迹与数据隔离

提供版本化schema（优先Parquet/Arrow及可读JSONL小样本），至少包含：

episode/source标识、版本/资源指纹、来源时间与engine tick、玩家视角、决策前观测、合法动作或mask、动作标签、标签语义、实际执行tick、反馈、reward及其版本、terminated/truncated、质量标记、来源与转换器hash。

1. 严格分离debug/oracle全状态与policy可见观测。对手手牌、精确圣水、未来事件、重建时才知道的隐藏种子不能进入策略特征或mask。
2. actor只能使用该时刻玩家可见/可推断的信息。若训练critic使用额外信息，必须独立配置、独立记录并测试其不会流入actor。
3. 合法mask不得利用敌方隐藏状态。按玩家真实能够观察的信息定义，不因局势重建拿到全状态就泄漏。
4. 观测必须在标签动作执行前采样，明确输入动作与部署动作的区别；不能把下牌后的状态用于预测同一次下牌。
5. 未行动时刻的WAIT是从采样网格构建的标签，必须记录决策间隔与标签来源；不能将“没有记录动作”无条件解释为人类明确选择等待。
6. 区分确认、推断、缺失和不支持，保存置信/质量原因。低可信样本默认隔离或显式加权，训练配置必须指定允许的质量等级。
7. 按整局/来源回放ID划分train/validation/test，同局换边、裁片、不同初始化假设或重复采集必须同组。检查近重复，避免伪造泛化。
8. 保存未过滤统计和过滤后分布；训练集质量依靠证据等级，不能把outcome_consistent命名为官方全轨迹gold。

导出后实际重新读取，检查schema、范围、单调时间、有限值、观测隔离、mask与动作、样本数量、文件SHA256。提供小型可人工追踪的episode样例及原始事件对照。

九、游戏画面与同局势渲染

优先运行与固定版本匹配的客户端/原生renderer，由真实战斗驱动画面。展示所用引擎、资源版本与来源。

- 至少显示一场真实数据重建对局的完整过程，提供可复现启动命令、实际截图、完整或可恢复分段录屏，以及对应episode/动作journal。
- 支持开始、暂停、继续和单步/定量推进；若原生renderer受限，提供实际可用范围，不在UI摆放无效控制。
- 显示手牌、圣水、塔血、单位、动作落点或事件；额外调试信息可用旁路面板，不要求修改游戏内部UI。
- 渲染和无渲染运行相同episode与动作输入，在起始、中段、终局等至少5个锚点比较语义状态。渲染帧率可以不同，战斗推进不能改变。
- 若无法共用同一运行时，必须从相同原始初始化与journal分别重建，并检验一致；不能把旧模拟器输出另画成游戏画面冒充原生复现。
- 不用预录视频充当可控制对局，也不以截图存在证明所有交互一致。资源授权不足时不能用擅自分发素材作为交付捷径。

自绘或近似美术界面可作为辅助工具，但不计入本阶段“配套游戏画面”硬验收；若只能做到辅助界面，明确主画面目标未完成。

十、批处理、恢复与最小学习验证

先完成正式100局批处理，保存逐局记录。提供任务队列、按episode断点续跑、worker状态、超时和有界重试。主动中断一次再恢复，验证无遗漏、无重复计入、产物不会被不完整文件冒充。
