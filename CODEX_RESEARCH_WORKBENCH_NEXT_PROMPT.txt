六、运行层的接续原则

逻辑结构保持三层：
研究模型/训练函数 <-> 实验服务/任务记录 <-> 原生运行与媒体适配。
CLI 与网页共用 ResearchService，不能各自实现配置解析和判定。首版保留本地 JSON/JSONL、一条后台队列、一个原生任务槽，不引入数据库、Celery 或分布式系统。
研究者通常只改 learning.py 的模型/loss、必要时的 observation.py/belief.py、以及显式实验配置。

统一入口沿用：
.venv-cloud/bin/python tools/cloud/workspace.py research
它当前已有路由但未完整验收，交付前必须实际可用。正常只暴露私有 8770 网页/API/视频入口；内部 ADB/RPC 仍留在回环地址。
离线训练、查看档案、播放已存录像不启动 Android，也不先占原生锁。不要因打开首页就构造 CloudNativeSession；其 worker 会长期持锁并挡住评估。
prepare 与批次控制的锁边界要明确：不要在已持 native_lock 时又调用会让子进程 native_prepare 取同一锁的 ensure_runtime，避免自锁。
一个世界只有一个时钟与控制者。录像编码可附着会话；不要让另一个 runner 或页面控制器同时 reset/advance。
重复启动通过应用握手和进程身份复用健康的本项目入口；不凭端口开放判断，也不杀未知占用者。
刷新只恢复任务查看；进程中断保留 interrupted 和准确的重试方法。不要盲目重发执行结果未知的 reset/出牌操作。
保留 Windows 入口、旧 CLI、历史模型、数据、磁盘和证据。只停止明确归属本任务的进程。

七、阶段 0 先做最小媒体实测

先检查现有资源、进程归属、可用内存/磁盘、编码工具版本和本项目控制锁，再决定是否启动运行端。不要读取凭据、自动付费扩容或重建用户已有磁盘。
由一个探测 runner 串行完成：
1. 复用现有准备函数，显式 rendered 场景，在 configure/reset 之前启动原生录制。
2. 保存 configure 前、reset 返回、动作请求/实际消费、停止录制时的 tick 与主机单调时间。
3. 用当前支持卡组至少验证一个实际消费动作和真实单位/塔变化。不能以成功注入代替消费确认。
4. 拉回真实媒体，做完整解码、PTS、尺寸、关键帧、时长、分段间隙与有效更新率检查；在目标浏览器试播放/暂停/前后 seek。
5. 分别报告“能录制与播放”和“适合实时互动”；不要求离线录屏必须达到实时 1x。

已有 native_media.py 选择 screenrecord，但不能因此假定编码器可用。它分段后拼接，需验证跨段间隙及真实媒体时间映射；仅 ffprobe 容器合法或文件非空不够。
如已有 screenrecord 路径不能满足需求，再依据实测评估 scrcpy 连续录制；工具支持录制不能证明当前 guest 支持。选定一种主路径，不同时重写两套媒体系统。
对于长于单段或可能缓慢运行的对局，必须实际覆盖段切换。既不把缺帧补成假画面，也不把拼接去掉的间隙藏在“完整视频”结论中。

八、阶段 1 和 2 具体交付顺序

第一步：补齐研究页面与离线流程。
- 页面提供训练、评估、实验/录像列表；后续人机入口在未完成时明确标状态。
- 从 catalog 选择数据、模型与预算，显示训练进度、曲线、验证结果、checkpoint 和失败日志。
- 用新 run_id 实际训练两轮，新进程加载保存 checkpoint 并验证；不碰 test。
- 核对重构前后一批冻结输入的编码、mask、解码和 hidden 更新，避免把重构造成的策略变化混入结果。
- 验证重复启动、刷新、取消和重开时的 interrupted 状态；离线操作的原生调用数为零。

第二步：接录制到原生评估。
- 补 CLI -> run_batch -> recorder 参数与生命周期、逐局媒体清单和所有异常/取消的收尾。
- 原生 reset 返回前会预热到 tick 90，不能等 reset 结束才录。录制在首次 configure/reset 之前就绪，结束在记录自然终局之后。
- 先运行少量预算内的新局；保留模型 owner、模型/数据/版本指纹、双方日志、消费反馈、终局和媒体。
- 默认两局配对评估，启动前固定录制索引 [0]，只录第一局以控制首版预算；新增内部 record_game_indices 或等价字段，在不可变配置中保存。研究者不必手工填写。
- record_video=true 表示开启录像，录哪些局由上述明确字段决定，不能同时又暗指全部局。选择全录时，全部所请求媒体通过才能标整体完成。不事后只挑赢局。
- 最小媒体里程碑是预先选定局从开始到自然终局的完整原局录像；另一配对局的数值结果与未录制状态如实保留。
- 保存媒体状态 requested/recording/complete/partial/failed/not_recorded 和失败原因，不把数值通过提升成媒体通过。

第三步：完成离线播放器和同步。
- 复用登记媒体与 Range 服务，用真实浏览器验证原生视频播放、暂停、倍速、开头/中间/结尾前后 seek。
- 停止 Android 后重复这些操作，确认不发 reset/advance、也不重新启动 VM。
- tick/20 只表示游戏秒，不能直接作为视频 currentTime；主机收到的 segment 事件也不是第一帧 PTS。
- 记录每段 PTS、主机/设备时间和 tick 锚点、段间空隙及误差。事件跳转只能定位到有证据的媒体时间区间；精确映射未知时标注范围，禁止伪造 video_seconds。
- 历史 headless 对局显示“当时未录制”。重演新录另存来源、运行编号与误差，不覆盖或冒称历史原局录像。

十、后续阶段 3 的设计边界

以 Windows 桌面镜像为实时客户端优先，训练继续在 Codespaces。由项目脚本自动准备连接、镜像与退出清理；一次安装和 GitHub 登录权限与日常操作分开。
当前 android_mirror 脚本默认 --no-control、5fps，未在用户 Windows 完成实测。取消 --no-control 不等于人机对战接通。
CloudNativeSession 当前是规则对手，StatefulPolicy 原生模型 runner 是另一条链。后续必须整合成一个会话调度器，不能启动两条链争同一世界。
自动持续推进游戏；双方动作归属/排队/实际消费和 AI hidden 状态由同一会话维护。默认每次出牌后不停住，暂停/单步只作为用户主动调试功能。
先证明原生触摸能在这个离线场景生效并归属正确；如不能，再选一种原生画面上的拖放控制层转换成规范动作。两种方式只完成一种，不双写，也不退回一步一点击的坐标表单。
只由拥有世界控制权的调度器提交或接纳人类与 AI 输入；镜像直接触摸若绕开这条链，必须先证明可归属、可审计且不会双重执行，不能默认开放。

互动目标先沿原任务书：约 1x 游戏速度、有效新鲜画面至少 15fps、期望 30fps、额外输入延迟 p95 不高于 300ms。先记录实际值，正式实现前冻结测量窗口和容差；这些不是当前已达成能力。
分开报告网络/排队/模型推理、决策节拍和游戏固有部署延迟。调高显示参数不能替代源游戏速度与新鲜帧验证。
如果当前 TCG 后端不达互动要求，保留已完成的训练和录像工作台；另列本地/硬件加速运行端的固定版本、ABI、探针、重置、观测/动作/时序兼容验证任务。可将保存 checkpoint 放到兼容运行端就近推理，不要求训练也搬出 Codespaces。

2. Android 官方 adb/screenrecord：文档列出单次录制默认/最大 180 秒；实现需核对当前 Android 工具版本，并验证长局分段边界。
   https://developer.android.com/tools/adb#screenrecord
3. scrcpy 官方远程连接：远端设备可经隧道连接；项目应封装必要连接，不能把原始手动步骤再交给研究者。
   https://github.com/Genymobile/scrcpy/blob/master/doc/tunnels.md
4. Codespaces 官方端口说明：可配置 forwardPorts，已有 Codespace 的配置更新生效需要重建。首版记录一次性设置和日常启动的区别。
   https://docs.github.com/en/codespaces/developing-in-a-codespace/forwarding-ports-in-your-codespace
5. Android 模拟器加速说明：图形和 VM 加速影响运行性能；不是本仓库固定版本/探针兼容性的证明。
   https://developer.android.com/studio/run/emulator-acceleration
