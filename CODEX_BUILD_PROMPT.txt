三、版本化的战斗模型与交互验证

先确定研究目标游戏版本/平衡日期，建立完整卡牌目录和来源快照。将卡牌数据、等级、塔兵种、进化/英雄和规则与引擎代码分离，能更新数据而不重写策略。

尽可能实现该版本的完整交互，重点核查：
1. 圣水恢复阶段、上限、部署延迟、手牌与下一张卡、轮转、合法部署区域、拆塔后的区域变化、加时和决胜规则。
2. 路径与桥、碰撞/推挤、体积、视野/索敌、目标锁定与切换、空地目标、建筑目标、拉扯、攻击间隔、首击延迟、弹道和范围伤害。
3. 法术的范围/持续时间/塔伤、击退、眩晕、减速、冻结、重置、护盾、冲锋、跳跃、穿透等特殊状态及其结算顺序。
4. 生成器、死亡衍生单位/伤害、持续建筑寿命、召唤数量、英雄技能与冷却、进化周期、国王塔激活和不同塔机制。

生成 machine-readable 的 card_coverage.csv、mechanic_coverage.csv 和 interaction_tests 清单。每项区分“已验证一致/近似实现/未验证/不支持”，给出版本、来源、实现路径、测试和误差。覆盖率必须说明分母；存在卡牌名称或数据行不代表行为已实现。

为关键机制和典型卡牌配对建立可复现交互测试，覆盖范围边界、结算顺序、组合效果和已知失败案例。可合法取得的录像或参考引擎用于差分/轨迹对照；只通过自写测试不能证明与官方一致。不要声称穷举了全部连续落点、时序和多单位组合。

四、本地服务器与真正可执行的闭环

实现统一 BattleBackend，至少包含创建/重置对局、推进固定 tick、获取观测、合法动作、执行下牌/技能、终局结果、随机种子、快照恢复、事件日志和回放导出。提供本地服务/API，并让无界面加速训练和交互界面使用同一个引擎。

界面应允许选卡组、手动下牌、观察 AI 对 AI 或人对 AI、暂停/逐帧、保存与加载局势、从历史局势分叉实验。展示手牌、圣水、塔血、单位/状态、决策落点、候选评分、对手信念及运行延迟。界面必须连接实际战斗状态，不使用另一个简化动画冒充引擎。

agent 自动完成：获取观测 → 维护历史/信念 → 生成与屏蔽动作 → 推理/搜索 → 向后端执行动作 → 检查接受结果与状态变化 → 记录轨迹 → 下一轮。支持跨多局自动 reset，处理超时、断连、重复动作和终局。必须实际执行下牌，不以打印建议或 dry-run 作为主闭环验收。

明确隔离三条输入路径：
A. 完整状态仅用于引擎调试/可选 oracle 基线。
B. 只包含玩家可见信息的主策略观测；隐藏对手手牌、精确圣水和未来事件不能泄漏。
C. 可选像素感知路径，使用真实游戏专用检测/OCR/追踪资料或模型，并报告识别误差。

主闭环在本地后端自动验收。没有设备时继续完成 A/B 路径；C 路径保留真实适配接口和明确未验证项，合成图片不得冒充真实截图识别成功。

五、可替换策略、训练与评估

建立统一 Policy/Agent 接口，将 observation encoder、opponent belief、action space/mask、candidate generator、search/world model、value/reward、policy network、trainer、evaluator 和 executor 分开。

至少实现并运行：随机/规则基线、带明确计算预算和对手假设的前瞻搜索策略、一个从专家/搜索轨迹训练的学习策略。提供能够实际启动的强化学习环境与短程训练入口，并按本机算力验证训练产生 checkpoint、加载 checkpoint 推理和完整对局；性能不佳应如实记录。优先使用可复用训练库，允许从小规模实验开始。

需要显式建模 WAIT、下牌时机、卡牌和落点，以及支持范围内的技能动作。对手信息维护卡组候选、圣水不确定性和轮转历史；区分确认事件与视觉推断。优化目标针对最终胜负和资源/塔伤权衡，不把短窗口最高分称为全局最优。

冻结测试场景、训练/验证按整局划分。使用多个随机种子、对称换边、不同卡组和至少三种对手策略，配对比较策略。目标每种主要策略至少 100 局；计算预算不足时报告实际数量并标明该项未达。记录胜/平/负、塔伤、非法/被拒动作、决策延迟 p50/p95、吞吐、崩溃/超时和训练曲线。区分等待帧与出牌帧，做至少一组有意义的消融，不把模拟胜率当作真实游戏胜率。
