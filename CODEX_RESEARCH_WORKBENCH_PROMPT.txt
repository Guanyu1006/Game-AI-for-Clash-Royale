一、用户希望得到什么

用户主要研究 AI 模型、训练方法和实验结果，不希望每次手工准备虚拟机、Android、身份文件、ADB、RPC 或多个转发端口。
日常操作应是：打开一个入口，选择数据和模型，启动训练或评估，查看进度、指标和真实对局画面。
需要能够点击播放、暂停、拖动进度条的原生画面回放。不要用另一套简化引擎重新画棋盘来代替原生画面。
后续希望在原生画面上自然选择手牌、拖放下牌，与所选训练模型连续完成一局；默认不停在每次下牌之后。
当前先设计、分阶段实施。不要把实时对战、算法提升和全功能科研平台同时作为一次改动。

浏览器优先是本任务书的暂定客户端方案，仍可根据用户后续偏好调整；Windows 桌面镜像可作为可选客户端，不要求日常手动建 SSH 隧道。

二、实际现状与不能混淆的能力

1. 仓库有 royale_ai、royale_lab、royale_phase2、royale_phase3 多套历史代码。新主线沿现有 phase3 学习链和 phase2 原生后端推进，其他引擎保留，不把不同引擎的实验成绩混用。
2. 当前主线是固定版本 Null's Royale Android 战斗库加离线探针，不是官方训练 SDK，也没有证明全部官方交互等价。
3. 云端 Python 运行策略与训练器；QEMU TCG 软件虚拟机内的 Linux 提供 Binder，Redroid 运行 Android，ARM 兼容层加载游戏库。复杂运行层来自当前远程环境适配，不是学习算法的组成。
4. tools/cloud/workspace.py 的 train、train-gru 读取保存数据，不产生新对局。默认历史数据、模型变体与 tools/native_loop.py 路线并不完全相同，不能无声混用。
5. tools/native_loop.py 已有 collect、export、train、evaluate、run。royale_phase3/native_loop.py 已有分阶段日志、独立输出、新进程加载和原生回合记录，适合复用。
6. 当前 _run_loop 内部的采集策略指定为 random。不要根据旧文档笼统称它是专家数据或高质量规则示范。来源、策略、版本和划分必须以实际保存配置为准。
7. tools/cloud/replay_app.py 已能复用或恢复已有 Android 安装并调用 native_prepare；但还不是统一实验服务。现有大资源与 VM 磁盘不随 Git 克隆到新机器。
8. 现有浏览器画面来自间隔 ADB screencap。默认 capture_ticks=100 相当于每五游戏秒存一帧，不是连续视频。
9. 当前保存画面的 mapping=None，不能认为图片点击到原生落点已可靠标定。现有输入主要走手牌按钮或辅助坐标，不是完整原生触摸操作。
10. tools/android_mirror.ps1 和 tools/cloud/android_mirror.py 有 scrcpy/SSH 方案，默认 --no-control，用户 Windows 端未完成实测。改变此开关不会自动联接动作审计和训练模型。
11. CloudNativeSession 连续推进目前使用规则对手；StatefulPolicy 的原生模型 runner 是另一条链。两个控制者不能同时操作同一个世界。
12. 保存的 native-run-002 模型采集和评估是 rendered=false，没有原始对局视频。日志可用于后续重演，但重演新录画面不能称为当时录像。
13. native_browser.import_archive 当前 owner=1 的默认不适合直接导入交替座位的 phase3 评估结果；展示模型侧必须读取原配置。
14. 默认 fair 观测排除非塔单位。这是当前学习能力限制。重构操作流程时不得偷偷放宽为 oracle，也不得宣称显示完整画面就等于模型看到了完整战场。

三、目标系统：统一使用方式，保持模型与基础设施分工

逻辑上整理为三层，不是再创建第五套引擎或训练框架：

A. 科研层：数据 -> 模型 -> 训练 -> 推理 -> 评估。
研究者主要修改模型结构、输入设计、训练配置和评价方案。
先固定一种现有小模型和八卡任务，以稳定重构前后的行为。不要同时更换算法、环境和数据。
初期复用 learning.py；只有在职责影响修改时再拆出模型/训练/推理文件，并保留既有导入兼容。

B. 实验应用层：一个入口、任务队列、实验编号、进度、模型选择、结果比较与回放。
CLI 和浏览器调用同一执行逻辑，不能分别形成另一套参数和判定规则。
首版复用现有 JSON/JSONL 和 outputs 目录组织，不为此先引入分布式调度或数据库服务。

C. 环境适配层：准备和复用 Android，管理连接与身份，串行驱动对局，采集实际反馈与媒体。
不在此层改变模型，也不把安装路径、PID 或端口要求暴露给每次实验。
软件 Android 是当前实现；为后续外部 Android/有硬件加速的运行端保留接口。首版不同时实现多种新运行端。

四、研究者可见的产品流程

规划入口（尚未实现）：
.venv-cloud/bin/python tools/cloud/workspace.py research

启动后只提供一个稳定私有网页入口，首选沿用 8770。首页只需四项主要操作：
1. 训练：选择经过登记的数据和模型配置，显示进度、训练曲线、验证结果及保存模型。
2. 评估：选择 checkpoint 和冻结评估方案，系统自动准备环境、运行新局、记录实际反馈。
3. 观看：选择某次实验和某一局，观看原生录像，查看该局结果与对应模型。
4. 与模型对战：后续阶段；选择同一份 checkpoint，进入连续人机对局。

可提供一个“完整实验”预设串起训练、验证、新局评估与选定局录像；同时保留纯离线模式。
首版只接入现有一种 metadata 协议和 GRU C，不先实现通用模型注册平台。默认组合固定为：本机已验收的 native-run-002 训练/验证数据、GRU C、现有八卡任务、冻结的 cycle 对手和配对换边评估方案；这些少量对局用于流程验收，不作棋力结论。
数据优先引用 outputs/native_loop_20261020/native-run-002/dataset/train_validation/metadata.json，启用前核对文件、划分与运行时版本兼容。缺少该数据时显示一次性导入/准备提示，不静默改用另一个来源；便携 pilot 如启用，仅作为明确独立的离线预设，不能假定与本机原生运行版本兼容。
纯离线训练或观看已保存视频不得因为页面启动而自动启动 Android。
用户一次安装/初始化可能仍需准备大型资源和登录已有 Codespaces 权限；区分首次配置和日常操作。
缺少磁盘、APK、编码器或连接权限时集中给出缺失项和一次性处理方式，不能让用户逐条猜内部端口。

页面中的研究配置只需暴露：数据、模型、训练参数、评估方案、预算。内部配置由后端解析。
能查看解析后的完整配置和证据，但不在正常操作里要求填写它们。
“当前对手：规则策略”与“当前对手：checkpoint 名称/指纹”明确区分；加载失败就报告，不静默退回规则策略。

五、运行时管理与端口收拢

1. 由一个运行时管理器复用 replay_app/native_prepare 的可靠步骤：检查现有实例、恢复已有安装、ADB 可达、内容就绪、当前身份、连接、稳定性。
2. 相同入口重复启动时识别并复用本项目健康服务；通过进程身份和应用握手判断，不只看端口开放。
3. 不杀未知占用进程，不恢复被其他控制者使用的磁盘。发生冲突时明确显示归属和可处理项。
4. 一个原生世界只允许一个持租约的调度器；评估、重演、人机会话等修改世界或逻辑时钟的任务排队或互斥。只读录像回看可以并行；同局的视频编码、直播分发和观看可附着于当前会话并行，不另取控制租约，需要探针状态时经持租约调度器读取。
   首版只需一个本地后台执行者、一个原生任务槽和 JSON 状态文件；CPU 与原生任务先串行，不引入 Celery、集群、数据库或通用工作流框架。
5. UI、API、进度和未来视频桥接走同一个对用户暴露的 HTTP/WSS 入口。ADB、游戏 RPC、媒体内部端口留在回环地址，不要求用户分别转发。
6. Codespaces 用 devcontainer 自动转发与可点击 URL 暴露该入口。旧 Codespace 的配置更新生效条件和测试结果要记录，不保证任何客户端策略下绝对零操作。
7. 原生进程重启后刷新身份与连接，不能继续信任旧 PID 文件。健康检查分清进程存在、内容就绪、对局可用和画面可用。
8. 页面关闭不等于正在运行的实验被取消。后台任务独立记录生命周期，重新打开能恢复查看；Codespace 关闭也不能保证任务持续。
   首版刷新恢复的是任务进度查看。后台进程已中断时显示 interrupted 与准确重试入口，不承诺自动恢复训练中间状态或原生局面。
9. 提供停止任务、释放对局和停止本项目运行时的操作。只停止明确拥有的进程，保留模型、日志、磁盘和媒体。
10. 对 reset、出牌、推进等结果未知的操作不盲目重试；保留失败现场。中断后的恢复从显式新局/已验收检查点进行，不伪装精确续跑。

六、统一实验记录与模型接入

每个实验拥有唯一 run_id，至少保存：
- 请求配置、解析后配置、代码版本/工作区差异摘要、数据与划分指纹。
- 模型变体、观测 profile、动作/坐标协议、版本指纹、训练种子与预算。
- 输入数据和初始模型引用，训练曲线，选定 checkpoint 和哈希。
- 阶段进度、stdout/stderr、开始/结束、失败原因、终态及可继续方式。
- 各局 episode_id、owner、对手策略、种子、原生日志路径、自然终局/截断/失败和实际消费。
- 离线验证与原生评估分开存放；界面明确结论范围。
- media 状态与文件：未录制/录制中/完成/部分/失败；录像来源为原局或新重演。

现有不同 CLI 的默认数据/变体必须收拢到显式配置，不按同一个按钮暗中选 C 或 D。
在线和离线使用同一输入编码、动作解码与 checkpoint 选择规则。按 episode/owner 重置隐藏状态；同 tick 不重复更新。
界面和归档从实际配置读取模型方 owner，不固定为 1。
卡槽、卡牌和位置的请求值与实际确认值保持区别。消费确认不自动证明落点独立核验。
数据继续按独立整局分组；留出测试集不用于日常反复调参。

七、原生回放：先保存真实视频，再提供点击播放

先澄清四种材料：
- 数值日志用于分析，不代表原生录像。
- 原局录屏是当次真实 Android 输出的保存视频。
- 日志重演是在引擎中重新执行并新录画面，必须标明“重演录制”。
- 公开 JSON 重演带有初始化等假设，不能冒充模型当时的原局。

目标回放：
1. 新的可视评估局必须显式使用 rendered 路径，不能沿用默认 rendered=false 后仅附加录屏。原生录屏在 configure-native/reset 前启动，保存到终局；当前 reset 内部会预热至 tick 90，返回后才录会漏掉前缀。先录少量代表性局，不默认让所有训练采样承担录屏成本。
2. 优先验证现有 Android 编码能力和 scrcpy 录制路径；固定实际使用的工具版本。scrcpy 支持桌面镜像和录制不等于当前 guest 编码器已经可用。
3. 输出可被目标浏览器播放和拖动的媒体文件，带时长、分辨率、实测帧率、关键帧/seek 能力与完整性检查。
4. 视频在 Android/VM 停止后仍可查看、暂停、倍速和拖动进度条。播放视频不得向原生后端发 reset/advance。
5. 保存视频 PTS/录制时间与引擎 tick 的映射锚点及误差。视频通常使用现实时间，不能直接把 tick/20 当作视频时间。
6. 点击动作事件跳到最近已验证时间锚点；边界显示同步误差。未独立证明像素时刻时，不宣称精确逐帧对齐。
7. 缺少原始录像的历史实验显示“未录制”，可另外申请重演录制；原日志和新录像来源不能覆盖混写。
8. 原生引擎的向后跳转当前依赖 reset+前缀重演；普通视频 seek 是读文件。不要把昂贵重演当作每次拖动播放器进度条。
9. 不用稀疏 PNG 轮播、插值补帧或简化棋盘冒充流畅原生录屏。临时截图仅作为明确标注的诊断材料。
10. 如果使用 host 编码或转封装，记录来源及派生关系，验证其实际原生画面和时间语义。

浏览器是产品入口，不要求重绘游戏。浏览器直接播放保存的原生视频是首版最稳妥的观看路径。
scrcpy 可作为桌面镜像工具；浏览器直播还需要服务器媒体桥接与浏览器解码，不能只把桌面脚本放进页面。
首版回放无需同时引入 WebRTC/STUN/TURN。直播传输方案在可行性测量后选择，维持单一用户入口。

八、连续人机对战：作为后续独立阶段

必须先验证四个能力：
1. 原生游戏与渲染能持续跟上目标游戏速度。
2. 能输出稳定、低延迟的真实原生画面。
3. 能把用户操作正确归属到人类一方并确认游戏接受。
4. 能在同一个世界中让选定 checkpoint 控制另一方。

会话结构：
- 一个调度器拥有原生控制权和逻辑时钟；人类输入与模型动作都进入它的队列。
- 自动连续推进，不要求每次出牌后点击下一步；暂停和单步只作为用户主动选择的调试模式。
- AI 使用该局自己的真实观测和独立隐藏状态，保持声明的决策节拍；不读取人类待提交输入或来源未来命令。
- 两方动作、提出/注册/消费时间、失败、游戏时钟与现实时间持续记录。
- 视频编码、网络与慢客户端不阻塞主要控制路径；媒体丢帧与动作失败分别统计。
- 不能继续启动另一个模型 runner 与 CloudNativeSession 抢世界，也不能保留规则对手同时冒充模型对手。

输入实现选择：
- 优先验证原生 UI 的触摸输入是否在当前离线场景有效，以及能否联接实际消费事件。
- 若采用原生视频上的手牌/拖放交互层，经校准把屏幕点转换为规范动作，再由统一调度器执行；这是原生画面上的控制层，不是简化引擎重画战场。
- 两种路径先选一种完成，不双写同一动作。缩放、留黑边、设备方向、蓝红方、手牌槽和原生坐标都需验收。
- 若外部镜像能直接触摸，仍要与同一会话归属/反馈记录一致；不能把关掉 --no-control 当作接通完成。

性能必须测量，软件 TCG 的源速度无法靠前端包装提高。
报告至少包含：游戏时间/现实时间比、有效画面帧率/新鲜度、浏览器输入到接收/注册/消费的延迟、模型推理延迟、CPU/内存和断流情况。
建议的后续互动最低目标为正常速度约 1x、画面至少 15fps（期望 30fps）、额外交互延迟 p95 不超过 300ms。
这是待实测并冻结的产品目标，不是现有能力；游戏自带部署延迟、模型决策周期和网络/排队延迟分开报告。
若当前宿主达不到，仍可交付离线训练和录屏回放；实时对战需选择通过同版本/ABI/探针/重置/时序验证的本地或有硬件加速运行端。
不得自动付费换机器，也不得擅自迁移到官方在线对战；把实际缺口、测量与候选适配成本报告清楚。

九、阶段顺序及明确交付

阶段 0：原生媒体与交互可行性实测。
- 不先搭大型新 UI。用当前资源验证短程原生画面、实际编码、一个动作消费和游戏/现实时间关系。
- 此阶段不开发直播桥接或新的触摸系统；只测已有路径可测的项目，阶段 3 的浏览器交互延迟可以保持未测。
- 分开判断“可录可播放”与“适合实时人机”，前者不要求实时达到 1x。
- 输出测量、原始媒体、实际命令、错误和明确结论，决定阶段 2 的录制方式及阶段 3 的运行位置。

阶段 1：统一研究入口与离线实验。
- 一条入口打开工作台，能选择现有数据和一个模型，真正训练、保存、新进程加载并验证。
- 统一任务状态和实验档案，能打开已有实验和中断日志；离线任务不启动 Android。
- 保留旧 CLI 为兼容入口，内部尽量复用同一实现，避免新旧两套运行逻辑漂移。

阶段 2：自动原生新局评估与原生录像回放。
- 在工作台选择模型和评估方案，自动准备/复用环境并串行执行。
- 单独记录 rendered 新局的配置和实测结果；历史 headless 评估通过不能替代该局渲染、时序与媒体验收。
- 至少一局从开始到自然终局的真实原生画面录像，绑定该局 checkpoint、owner、日志与终局。
- 在停止 Android 后仍可在同一页面播放、暂停和拖动这段录像。
- 这是首个纵向最小可用版本：训练 -> 保存模型 -> 新局评估 -> 指标与原生录像。
- 若资产或编码能力受阻，阶段状态明确为未完成并保留可用的离线成果，不用截图或合成图冒充过关。

阶段 3：连续与所选模型对战。
- 阶段 0 的互动性能条件满足后实施，按第八节完成统一会话、输入、直播与录像。
- 至少完整完成一局自然终局，能证明操作者与模型双方的动作归属；人类方无需单步按钮。
- 人机体验用于直观诊断，不代替多局冻结条件下的策略强度评估。

阶段 4：改善科研输入与算法。
- 在流程稳定后，先补齐完成任务必需且经核验的观测，再研究历史、记忆或其他模型改动。
- 逐项控制变量；本次基础设施重构不同时宣称策略提升。

十、首个可用版本的验收方法

A. 易用性
- 新开终端只需统一入口；无需手工编辑 identity/connection 或分别转发 ADB/RPC。
- 重复启动识别本项目服务并复用；刷新页面能继续查看原任务。
- 离线训练和离线录像回看均不启动 VM，原生任务才申请运行时。
- 开始原生任务后阶段进度可见，失败能定位到准备、建局、推理、执行或录制。

B. 模型真实性
- 保存模型经独立进程加载；页面显示的模型指纹与该局实际加载回执一致。
- 训练、验证、部署共用兼容编码与解码，错误版本/观测 profile 被明确拒绝。
- 真正使用训练模型的动作与规则对手分开记录，不以成功入队代替实际消费。

C. 对局证据
- 全部请求局都列出；自然终局、截断、失败分别统计，不只选择成功局计算好看结果。
- 保存配置、观测、请求、实际事件、胜负和对手身份；run/episode/owner 能相互追溯。
- 成功推进与棋力提升分别报告，少量试运行只验收流程。

D. 原生媒体与播放器
- 画面确实来自该运行端的 Android，能看到真实战场单位、手牌或塔的变化；不是静态图或另一引擎。
- 新录局覆盖对局开始至终局，文件可解码、时长和缺帧情况可核对。
- 播放、暂停、倍速、前后 seek 至少覆盖开头、中间、结尾；停止 VM 后仍工作，回看不推进引擎。
- 点击事件定位到有记录的时间锚点，误差和“原局录制/新重演”来源标记正确。
- 目标浏览器的真实页面完成一次完整流程验证；fixture 和单元测试不替代真实媒体与原生对局。

E. 后续实时人机（不作为首版已完成条件）
- 普通玩家方式在原生画面上选择/拖放，游戏持续运行至终局。
- 所选 checkpoint 真正控制对手，模型 hidden 与双方 owner 正确，未混入规则代打。
- 出具时钟、帧率与输入延迟报告；未达到互动门槛不标成正常速度实时模式。

十一、迁移和开发约束

1. 下一轮先完成阶段 0，再实施阶段 1、2 的最小纵向版本。阶段 3、4另行推进，不要求在同一次修改全部做完。
2. 先记录现有基线和行为，新增统一入口与适配；验收通过前不删除历史包、模型、数据、Windows 启动器和旧命令。
3. 复用现有原生 backend、动作消费反馈、数据协议、StatefulPolicy 和训练函数；不重新写战斗规则。
4. 所有文件、缓存、媒体与输出保留在仓库内，新结果使用独立目录，不覆盖原始证据。
5. 使用 .venv-cloud/bin/python 显式解释器。新增依赖更新适用清单，不覆盖历史 Windows lock。
6. 根据改动验证任务状态、模型加载、坐标/owner、单控制者、失败保留、媒体 seek、离线模式零原生调用及兼容入口。检查以真实行为为准，避免只测试 mock 自己。
7. 运行原生前检查当前资源与进程，不根据历史已启动/已停止描述擅自判断现状。
8. 保留现有接口访问检查与私有端口，不为方便浏览器镜像直接公开 ADB 或游戏 RPC。
9. 模型可见信息限制不能在操作重构中被悄悄改变；研究 oracle 与公平 actor 始终分开。
10. 阶段验收分别给结论：代码检查通过、离线训练通过、原生新局通过、原生媒体通过、实时人机通过、策略提升有证据。没测的保持未测。
