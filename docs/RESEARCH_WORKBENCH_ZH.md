## 三步开始实验

1. 在仓库根目录打开终端，运行：

   ```bash
   .venv-cloud/bin/python tools/cloud/workspace.py research
   ```

   打开终端给出的网页，或 Codespaces 的 **Ports / 端口 → 8770**。保持端口为 **Private**。正常操作只用这一个入口，不需要分别准备 VM、ADB、身份文件或转发游戏内部端口。保留这个终端运行。

2. 左侧选择 **训练**，数据选 `native-run-002`，模型选 **GRU C**。第一次保留默认两轮，点击 **开始训练**。这是保存数据上的离线训练，不启动 Android。

3. 右侧查看实验阶段、训练曲线和验证结果。每次提交都有独立实验编号；刷新或重新打开页面，可以在 **选择实验** 中回到原任务。新模型出现在模型目录后，可切到 **评估** 并选择该 checkpoint；也可选 **完整实验**，依次运行训练、验证、新局与录像。后两条原生流程当前仍待实机验收。

第一次克隆仍需准备依赖和经过审查的数据；完整 Android 安装盘、APK 和大型素材不随 Git 克隆。首页会说明哪些已登记数据缺失，不会悄悄换数据或用规则策略替代模型。初始化说明见 [Codespaces 指南](GITHUB_CODESPACES_ZH.md)。

## 怎样判断结果

右侧把不同证据分开展示：

| 看哪里 | 能回答什么 |
|---|---|
| 训练曲线、验证动作 NLL、出牌事件指标 | 模型是否完成优化，以及在保存的验证观测上怎样预测 |
| 自然终局 / 请求局数、胜负、消费确认 | 模型在新的原生对局中是否真正执行，以及哪些局完成或失败 |
| 逐局录像状态与播放器 | 是否保存了这局真实 Android 输出，录像是否完整、能否回看 |
| 配置、checkpoint 指纹、执行证据 | 本次到底用了哪份数据、哪个模型、什么预算和版本 |

不要只看召回率或动作准确率。比如本次离线验证出牌事件召回率为 100%，精确率为 37.5%：它找到了已有出牌窗口，同时提出了不少额外出牌。这不等于原生游戏中都能执行，更不等于赢得对局。

已通过的真实离线实验为 `run-20261107t055223761604z-0ccb3619`。它使用两轮 GRU C 优化，新进程验证覆盖 1 局、352 行，动作 NLL 约 0.2314，刷新没有重新提交任务，未向模型提供 test 行，未调用原生 RPC。见 [真实浏览器与训练报告](../outputs/cloud/research-acceptance-20261107T054146Z/browser/offline-report.json)及 [实验记录](../outputs/cloud/research/run-20261107t055223761604z-0ccb3619/run.json)。这些报告在本机 `outputs/`，不保证出现在全新克隆中。

## 原生评估与录像怎样使用

首版评估固定为 **cycle 规则对手、同 seed 换边的两局**。两局都使用原生渲染路径；默认在启动前固定只录第 0 局，也就是页面中的“第一局”。另一局的数值结果与未录制状态同样保存。选择“录制所有请求局”时，全部所请求录像都必须验收，不能事后只挑赢局。

完整媒体交付目标是：所选 checkpoint 控制模型方，一局从首次 configure/reset 之前录到自然终局；两个配对新局的数值执行均通过。**当前这条完整链路未通过。** 本次实际评估编号为 `run-20261107t065103723813z-692b2ba4`：请求两局、实际尝试一局，在预热 `advance-native 89` 等待响应时超时；控制方决策与出牌均为 0，未继续第二局，分母仍为 2。这不是 AI 输局，也不是模型已经完成对战。

有已登记录像后，在 **原生对局录像 → 对局** 中选择，直接用播放器播放、暂停、倍速或拖动进度条。画面来自 Android 保存文件，不会再画一套简化棋盘。点击有已验证时间锚点的出牌事件，可以定位到对应视频区间；界面显示误差口径。没有锚点的事件禁用跳转，不用 `tick / 20` 假装精确的视频时间。

任务结束后可点 **停止本项目 Android 运行时**。已保存的录像不依赖 Android 继续运行，仍从同一页面回看；**页面服务终端需要保持运行**。播放录像只读文件，不重置或推进原生世界。

本次保存了约 **273 秒、360×640、72 帧**的真实 Android 初始化/预热片段，状态为 `partial`；画面可见原生战场与塔，但未记录到模型开始决策或完整终局。已在 Chromium 实测播放、暂停、2 倍速及前后 seek，点击页面停止 Android 后重载网页并重复通过，原生 wire 文件哈希不变，VM 未重启。见[真实浏览器报告](../outputs/cloud/research-acceptance-20261107T054146Z/browser/native-playback-report.json)。该证据只通过“部分原生视频的离线播放器”，不能提升为完整 D；该局没有可核验的动作时间锚点，页面不会编造出牌跳转。

历史 headless 实验显示“当时未录制”。如果以后用日志重新执行并录屏，会作为新的“重演录制”保存，不能冒充历史原局录像。现有原生版本与历史局部画面的范围见 [原生视觉指南](NATIVE_VISUAL_ZH.md)。

## 当前运行端的实测限制

当前云端使用软件 TCG Android。未录屏的短原生测试中，tick 90→120 的 1.5 秒游戏时间需要约 34.34 秒墙钟时间，约 **0.044x**；其中约 91% 花在原生推进 RPC。该局实际消费了两次出牌，但在 tick 120 按预算截断，没有自然终局。热复用准备检查实测约 19 秒；它减少重复准备，无法消除每局重置和推进的成本。

按这个短窗口线性推算，180 秒游戏时间可能需要约 70 分钟/局；这只是预算估计，未包含录像开销，也不是完整对局实测。录屏实测进一步遇到单次原生预热 RPC 超时：本次请求预算虽为每局 600 秒，底层单次响应的 180 秒限制先到达；提高页面预算本身无法解除这个限制。因此当前不要把“完整实验”当成已验证的快速自然终局入口。失败/截断保留请求分母；未知推进结果不自动重发，当前 VM 已停止。

当前 guest 的 AVC 编码器探测失败，临时开启 Codec2 的受控检查也失败，已恢复原设置。因此新路径采用 **连续 Android FrameOutput → 主机 FFmpeg VP9/WebM**；Android 原生画面不经过网页重画。输入没有源捕获 PTS，保存的主机收帧/喂帧时间只提供视频导航区间，画面年龄和精确呈现延迟仍未知。后续自然终局录像还须核验终局画面，不能只凭终局后收到一帧就通过 D。

连续通道验证同时发现并修复了两项真实问题：该设备的 `exec-out` 不能按预期接收脚本，改用无 PTY 的 `shell -T`；wallclock PTS 初次带 Unix epoch，改为只平移首帧原点，并严格校验起点与容器时长。原失败记录保留，见[修正后短录核验](../outputs/cloud/research-acceptance-20261107T054146Z/native/performance-recording-corrected.json)。静止源帧经有损编码后，解码 hash 也可能变化，不能把解码变化率当作新鲜画面 FPS。

详细游戏速度与输入指纹见[性能报告](../outputs/cloud/research-acceptance-20261107T054146Z/native/performance.json)。流畅人机对战需要先验证兼容且更快的运行端，Windows 镜像本身不会加速游戏。

## 失败后只查一个地方

在右侧选中失败实验，先看失败摘要，再展开 **查看配置、模型指纹与执行证据 → 阶段日志**。这里集中显示实验配置、日志路径及部分日志尾部；原生准备日志也保留在该实验的运行时目录。不要按猜测重启不同组件。

**停止任务** 会请求后台收尾并保留模型、日志和部分录像。关闭网页不会取消任务；停止页面服务或 Codespace 会中断后台执行。重开服务后，未完成任务标记为中断，不会假装恢复原生局面。修正明确的问题后重新提交，系统使用新实验编号，保留旧现场；未知结果的 reset 或出牌不会自动重发。

## 科研时主要改什么

| 研究问题 | 主要修改位置 | 保持一致的约定 |
|---|---|---|
| 网络结构、损失函数、训练方法 | [`royale_phase3/learning.py`](../royale_phase3/learning.py) | 训练、验证、新进程加载与部署使用兼容的模型和动作解码 |
| 模型输入、公开历史与 belief | [`observation.py`](../royale_phase3/observation.py)、[`belief.py`](../royale_phase3/belief.py)，以及相关数据契约 | 明确公开、推断、未知与 oracle 边界；修改后核验数据与 checkpoint 兼容性 |
| 训练预算、种子、对局预算 | 显式实验配置与工作台参数 | 整局切分、不反复用 test 调参、保存配置与指纹 |

先复用当前 C 模型跑稳定流程，再独立研究模型改动；新变体需要明确接入训练、保存、加载和评估契约，不能只改页面名称。运行层负责准备 Android、单控制者调度、消费反馈和媒体，研究者不必每次进入这些内部步骤。

当前固定 C 使用 713 维 fair 输入，**排除全部非塔实体，包括己方单位**；画面里能看见部队，不代表模型输入已经包含它们。数据只有 3 个训练整局（1113 行、85 次出牌）和 1 个验证整局（352 行、27 次出牌），无 test。这是工程流程样本，不能支持策略强度结论；来源是原生自采，当前完整采集流程使用 random 策略，不能称为专家示范。

这版工作台尚未实施世界模型研究流程。已有可选预测辅助头，不等于经过验证的多步世界模型或 Dreamer 想象训练；当前 C 的 world 分支关闭。可信战场观测、数据扩充、世界模型及算法对照按 [阶段三研究任务书](../CODEX_PHASE3_PROMPT.txt)另行实施，不在入口重构中宣称完成。

## 与同学讨论下一步

当前可先使用离线训练工作台讨论模型结构、输入与 loss。后续工作按这三个边界分工：

1. **运行基础**：核验更快运行端与固定版本、ABI、探针、reset、观测、动作及时序的兼容性；同时让单次 RPC 超时与实验预算有明确关系。当前失败发生在模型决策前，不能靠换模型解决。不得简单放大超时便宣称系统高效。
2. **原生验收**：运行端准备好后，再用同 checkpoint、同 seed 换边两局，覆盖控制方真实消费、自然终局及预选第 0 局完整原生录像。重新创建实验，不恢复或重发本次结果未知的推进。
3. **算法研究**：沿阶段三任务书，先明确可信观测、数据整局划分与评价协议，再独立接入模型/世界模型对照。当前 fair 输入不含普通部队，小数据和短测不能证明策略提升。

修复或更换兼容运行端后，可在页面选择上述 checkpoint 重新评估；也可复用已保存的请求生成新实验（先保持工作台服务运行）：

```bash
.venv-cloud/bin/python tools/cloud/workspace.py research submit --config outputs/cloud/research/run-20261107t065103723813z-692b2ba4/request.json
```

这会创建新编号，保留失败现场；该请求仍是 `max_tick=120` 的短测，不能据此通过自然终局。完整验收应在页面明确设置覆盖自然终局的预算并保存新配置，当前不要无条件重跑原生链路。

阶段 3 优先采用 **Windows 原生镜像窗口**：研究训练继续留在 Codespaces，用户用鼠标选牌/拖牌，与选定的同一 checkpoint 连续打一局。项目启动器负责连接；同一调度器拥有世界时钟并处理人类和 AI 输入。现有镜像脚本默认禁止控制，当前规则对手与模型 runner 也尚未合并，所以“取消 no-control”不能算接通。运行端需先证明游戏速度、有效画面更新率、输入延迟及版本兼容性，再决定是否需要本地或硬件加速运行端。

## 首次配置与旧入口

新 devcontainer 配置会自动转发并打开私有 8770；已有 Codespace 首次应用该配置可能需要一次 **Codespaces: Rebuild Container**。这是一次性配置步骤，日常继续运行上面的 `research` 命令，不要每次重建环境。

旧 `workspace.py serve` 和 `workspace.py play-replay` 继续保留。`serve` 的旧页面仍使用 8770，与新工作台不能同时占用同一端口；先结束旧页面服务再启动需要的入口。`play-replay` 的旧原生/公开回放页面使用 8772，新 devcontainer 不再自动转发它，需要使用时在 Ports 手动添加一次并保持 Private。旧原生页面与新评估不能同时控制同一个世界；原有 Windows 启动器、模型、数据和历史结果保留。
