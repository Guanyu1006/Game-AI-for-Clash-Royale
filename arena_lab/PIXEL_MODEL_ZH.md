# 真实截图与学习策略之间的缺测边界

旧 `arena-public-v2` 包含精确 HP、时钟、状态和己方轮转等数值字段。截图检测器目前不能可靠读出全部字段。把未知 HP 填为 0 会让网络把活单位视作死亡；把慢速 Android 的墙钟间隔当游戏逻辑时间，又会破坏时序模型。因此旧 checkpoint 不接受直接像素桥接。

`pixel_policy.py` 新增 `arena-masked-pixel-v3`。每个全局／实体特征都有对应 known mask；未知数值置 0 且 mask 为 0，两者一起进入网络。当前支持固定 8 张基础卡，保留已识别手牌、保守圣水下界、可见单位类型和位置。HP、时钟、皇冠、等级、特殊状态、技能按钮及未经校准的阵营判断保持未知。超容量拒绝，不悄悄截掉单位。

训练输入通过 `pixel_data.py` 从独立同版本自采数据投影，去掉与截图不可同等取得的字段。部署使用相同 schema 和坐标转换。它是**从模拟器向像素输入迁移的候选**，尚未包含真实检测器误差训练，不能把投影数据叫作真实像素监督。

## 输入、动作和时间

截图下方控制方的原生坐标向下，模型坐标以己方为起点向上；转换为 `x/18000, 1-y/32000`。模型 18×32 格点输出再逆变换为原生坐标。落点使用与引擎二进制绑定的 `visual_geometry_v1.json`：公开初始地图、六塔存活几何和两座位交集，普通兵242个保守候选、Cannon240个、法术576个。运行时不读取当局 oracle 掩码。普通卡仍限己方前15行，未知技能禁用；识别未知、圣水下界不足时只有 WAIT 合法。这些是静态候选，开场锁定、决胜结算和动态占位尚未由像素可靠识别。

战场特征只读取 `PixelObserver` 的截图结果，不读取原生完整状态、敌方手牌或圣水。原生状态可单独保存为对齐审计目标，不能经过桥接混入 actor。

墙钟只用于采集延迟。慢速或暂停推进的 Android 中，墙钟秒数不等于游戏秒数；只有控制器自己已确认完成的 `control_feedback.elapsed_ticks` 可以提供逻辑经过时间。没有这项证据时清空循环记忆，明确记录 `elapsed_game_time_known=false`，不会假装每帧经过 0.5 秒。该退化路径仍需单独评估。

```bash
.venv-cloud/bin/python -m arena_lab.pixel_data \
  --index outputs/arena-next-20261113/data-pixel-native8-v1/index.json \
  --output outputs/my-pixel-projection

.venv-cloud/bin/python -m arena_lab train-timing \
  --index outputs/my-pixel-projection/index.json \
  --output outputs/my-pixel-model --epochs 12 --threads 1
```

设备入口传入 `--checkpoint <masked-pixel-v3 best.pt>` 后使用 `PixelModelController`；它严格拒绝旧 v2 模型。不同屏幕分辨率、画面布局、卡牌图案或阵营识别变化，需要重新校准和新像素验收。正式实时标准应覆盖帧新鲜度、全局端到端 p95 延迟、实体漏检/误检、追踪失配、动作视觉一致性和完整自然终局；不能仅凭检测器返回框或 ADB 返回成功判定达标。

## 已交付模型与独立测试

`artifacts/pixel-masked-v1.pt` 为实际训练后的313,510参数 TimingGRU，大小1,330,919 bytes，SHA256 为 `a17c8fa67393fc38d691f5001fdaee17f4f4b9c5d8117ad6a2c0000a2d442f03`。12轮预算全部完成，monitor选择第12轮，共2,756次优化器更新。权重、训练元数据、有限数值、部署控制器重建和冻结前测试哈希均已核对；完整静态几何保存在模型身份内。

训练源是50局规则教师轨迹，30／10／10整局划分，再拆为27局拟合、3局monitor、5局校准、5局独立validation check和10局test。原始48,952个双方观察中，源教师出牌4,088次，投影后可监督动作只有2,617次（train1,608／validation542／test467）；1,471次不满足可观察标签条件的动作保留为无效标签，不能把源动作总数冒充有效像素监督。最终索引为 `data-pixel-projected-geometry-v2/index.json`；早期投影及修复前索引保留，v3计划在首次拟合前修正了源manifest路径和静态几何。几何修正没有改变此次有效标签数量。

阈值0.121200457、hazard温度与缩放只在5局calibration上拟合，并与权重一起写入 `frozen-before-test.json` 后才评估test。最终10局上的结果为：

| 指标 | 完整投影观察 | 同一模型移除战场实体 |
|---|---:|---:|
| 出牌时机 precision | 27.30% | 14.39% |
| 出牌时机 recall | 85.01% | 65.31% |
| 完整动作精确率（467个有效动作） | 47.11% | 24.20% |
| 给定真实卡牌的落点平均误差 | 1.48格 | 5.26格 |

实体消融说明策略确实使用了战场位置，但precision较低：在8,879个有效测试时刻预测1,454次动作，真实有效动作467次。这不是拥有高召回就足以实战的结果。与80局数值数据上的模型使用不同标签集合，不能直接把这张表与数值模型比较后宣布提升。

12轮实际训练时间累计1,177.34秒、316,164个有效标签更新，约268.54标签／秒。报告记载的累计会话时间1,332.09秒含校准与测试，不包含容器停机，且不能据此补全未保存的中断工作时间。本次为1线程CPU、并行研究负载下测量，不是独占吞吐峰值。

## 40局封存闭环与拒绝原因

`configs/arena-lab/pixel-evaluation-next-v1.json` 在首次拟合前确定，另存freeze SHA后才运行：10个新种子、随机／规则两类对手、双方换边，共40局。模型和阈值未据结果改动。新对手池与 `MaskedArenaEnv` 使用完整身份校验；随机对手使用投影候选，规则对手保留普通公开数值观察，其信息强于像素候选。

| 对手 | 自然结束 | 胜／负 | 请求／实际消费／拒绝 |
|---|---:|---:|---:|
| 随机 | 20/20 | 19／1 | 506／485／21 |
| 规则 | 20/20 | 3／17 | 636／607／29 |
| 合计 | 40/40 | 22／18 | 1,142／1,092／50 |

无故障、无截断，全部请求已对账。14,955个控制决策耗时61.90秒，约241.59决策／秒。拒绝率4.38%，超过1%可靠性门槛；每对手仅10个种子簇，也未达到正式晋升要求的25簇。结果明确标成 `independent_visual_evaluation_not_promotion`，原runner误标为promotion的计划和summary另存保留，不能把40局功能完成说成晋升通过。

另用新开发种子930001–930003、双方座位共6局定位拒绝原因，保持相同权重和阈值。6/6自然终局、238请求／224消费／14拒绝，耗时12.00秒；14次均逐条保存观察、动作历史和独立审计字段。2次为 `TOO_EARLY`，都发生于tick80，早于90tick开局锁定解除；12次为 `GAME_OVER`，集中于tick6000–6160。固定引擎的 `DeployRules.plays_stopped` 明确规定，加时结束后的扣血决胜动画尚未结束时也拒绝全部动作。本组没有费用、静态几何或动态占位拒绝；这识别出具体故障机制，不能反向把全部50次封存测试拒绝都按同一比例分类。

问题在于策略没有已知时钟／阶段输入，静态候选又故意不读取私有就绪信息。下一步应从独立标注的截图验证开场／对战／决胜／结果阶段及卡牌按钮就绪识别，在非行动阶段或阶段未知时阻止提交，并保留请求—回执—消费账本；不能给actor偷偷接入后台tick或原生合法掩码。阶段识别修改需使用新开发数据与新封存对局验收，不再调当前40局的阈值。

最终打包入口还完成像素模型两局smoke：2/2自然结束，89请求／83消费／6拒绝。其 `passed=true` 只表示权重重载、自然结束、存在真实消费且账本完整，**不表示低拒绝门槛、棋力或真实设备验收通过**。
